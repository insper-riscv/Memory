# Memory Contract

This document defines the contract that a memory block meets for whoever uses it, be it the core, a cache or a bridge. It holds for RAM, ROM, FLASH and SDRAM, inside the FPGA or outside it, and does not depend on the technology of the block. The protocol as seen from the core side is in [02-barramento-e-memoria.md](https://github.com/insper-riscv/Core/blob/main/docs/en/contracts/02-barramento-e-memoria.md).

## 1. Pins

Let $W$ be the width of the stored word, in bits, and $B = W/8$ the number of bytes in a word. A block with $N$ words has $N = \text{size in bytes} / B$.

| Pin | Direction | Width | Function | RAM | ROM |
| :--- | :---: | :---: | :--- | :---: | :---: |
| `i_clk` | input | 1 | Clock of the block, which can be the core clock or another one (section 4) | yes | yes |
| `i_addr` | input | $\log_2 N$ | Address of the word, not of the byte | yes | yes |
| `i_re` | input | 1 | Enables the read | yes | yes |
| `i_we` | input | 1 | Enables the write | yes | no |
| `i_data` | input | $W$ | Write data | yes | no |
| `i_mask` | input | $B$ | Byte mask of the write, one bit per byte, with `1` to write the byte | yes | no |
| `o_q` | output | $W$ | Read data | yes | yes |

A 256 KB RAM with $W = 32$ has $N = 65536$ words, so `i_addr` has 16 bits.

### 1.1. Correspondence with the blocks of the repository

The names of the contract follow the `i_` and `o_` prefix of the CONTRIBUTING. The Quartus IPs have names generated by the wizard, and the simulation models have names of their own.

| Contract | Quartus IP | `ram_simulation` | `rom_simulation` |
| :--- | :--- | :--- | :--- |
| `i_clk` | `clock` | `i_clk` | `i_clk` |
| `i_addr` | `address` | `i_addr` | `i_addr` |
| `i_re` | `rden` | `i_re_ram`, together with `i_en_ram` | `i_re` |
| `i_we` | `wren` | `i_we_ram` | none |
| `i_data` | `data` | `i_data_in` | none |
| `i_mask` | `byteena`, only in `ram` | `i_mask` | none |
| `o_q` | `q` | `o_data_out` | `o_data` |

The ROM IPs (`boot_memory` and `flash_store`) have `wren` and `data`, because the FPGA memory block is the same as a RAM one, but the board design keeps them at zero. The `rom_simulation` also has a second read port, with `i_addr2`, `i_clk2`, `i_re2` and `o_data2`.

## 2. Timing

| Operation | Condition at the rising edge of `i_clk` | Effect |
| :--- | :--- | :--- |
| Read | `i_re` at `'1'` | `o_q` carries the word of `i_addr` from the next edge on, one cycle later |
| Write | `i_we` at `'1'` | Each byte whose position in `i_mask` is `'1'` is stored, and the other bytes do not change |
| Core load | `i_mask` at zero | There is no write |

Beyond the table, the contract fixes the following.

- Bytes follow the little-endian order, with byte 0 in bits $[7:0]$ of each word.
- The internal blocks have no reset. The initial content comes from the initialization file (`.mif` or `.hex`), and the ROM only changes by external rewriting, such as the JTAG one, never by the core.
- A read and a write in the same cycle are not part of the contract. The `ram_chip` and the AXI bridge, if they receive both requests, let the write win. With a read and a write at the same edge and the same address, the simulation RAM returns the old value.
- The value of `o_q` with `i_re` at `'0'` is not defined by the contract. Whoever reads uses `o_q` only in the cycle after an `i_re` at `'1'`.

## 3. Variable-latency memories

SDRAM, FLASH behind a cache and external RAM take several cycles, and the one-cycle response of the contract above is not enough. These chips add two pins and use the 32-bit byte address instead of the word address.

| Pin | Direction | Function |
| :--- | :---: | :--- |
| `o_ready` | output | Level that rises when the data is ready and stays at `'1'` until the `advance` |
| `i_advance` | input | Tells that the request was consumed, and the chip can accept the next one (in the `ram_chip` it is called `i_mem_advance`) |

The request (address, data, mask, `i_re` and `i_we`) stays stable until `o_ready` rises, and the read data only changes at the next request. A line request adds `i_line`, which moves four words, and three extra 32-bit ports for words 1 to 3 of the data and of the read. The chips documented with this contract are [ram_chip](../ram/ram_chip.md), [flash_chip](../rom/flash_chip.md) and, on the SDRAM side, the bridge [sdram_cpu_bridge](../ram/sdram_cpu_bridge.md).

## 4. Clock

The clock is a separate pin, and the block only sees the edge it receives. There are two cases.

| Case | When it happens | What to do |
| :--- | :--- | :--- |
| Same clock as the core | The internal blocks of the board, such as the `BOOT_MEMORY` (wired to the `pll_clk_if` clock) and the FLASH storage (wired to `pll_clk_idexmem`), both 50 MHz clocks of the core | Wire directly, with no synchronization |
| Different clock | The SDRAM controller and the debug port, at 142.857 MHz, while the core runs at 50 MHz | Cross the domain with a request that toggles one signal (`req_tog`) and a response that toggles another (`ack_tog`), each read through two synchronizing flip-flops, with address, data and mask stable from the toggle of the request until the response |

The crossing by toggling is what the bridge [sdram_cpu_bridge](../ram/sdram_cpu_bridge.md) and the arbiter [sdram_arbiter](../ram/sdram_arbiter.md) use. A block must never receive `i_re`, `i_we` or `i_addr` from a clock domain other than its own without going through this synchronization.

## 5. Dual-port memory

A dual-port memory has two independent sets of access pins, and each port serves one access per cycle at the same time as the other. The contract of sections 1 and 2 holds for each port, and port 2 repeats the pins of port 1 with the suffix `2`, as in the `rom_simulation`.

| Port 1 | Port 2 | Function |
| :--- | :--- | :--- |
| `i_clk` | `i_clk2` | Clock of the port, which can differ from the clock of the other port |
| `i_addr` | `i_addr2` | Address of the word |
| `i_re` | `i_re2` | Enables the read |
| `i_we` | `i_we2` | Enables the write, only on the ports that write |
| `i_data` | `i_data2` | Write data |
| `i_mask` | `i_mask2` | Byte mask of the write |
| `o_q` | `o_q2` | Read data |

There are three arrangements of ports, and the repository uses two of them.

| Arrangement | Ports | Where it appears |
| :--- | :--- | :--- |
| Two reads | Both only read | The `rom_simulation` reads the same array through two ports, each with its own clock. The Core uses the second one to read FLASH constants in the MEM stage (`o_flash_addr2` and `o_flash_rden2`) while the IF stage fetches instructions |
| One read and write and one read only | Port 1 reads and writes, and port 2 only reads | The `ram_chip` has the data port of the core, the instruction port (`i_ins_*`) and the per-word debug port (`i_dbg_word_addr`), all with `o_ready` and `advance` |
| Two read and write | Both read and write | No block of the repository. Every Quartus IP uses `SINGLE_PORT` |

The usage rules are these.

1. Each port meets the timing of section 2 with its own clock. If the clocks of the ports differ, whoever drives each port crosses the domain as section 4 describes.
2. Two reads of the same word, one on each port, do not interfere with each other.
3. A write on one port and a read of the same word on the other, in the same cycle, have a result that the contract does not define. Whoever uses the memory must avoid the case. In the `ram_chip`, a read requested after a write has already completed sees the new data, including a store of the data port seen by the instruction port.
4. Two writes to the same word, one on each port, in the same cycle, are also undefined and must be avoided.

### 5.1. When there are no two ports

Two agents that need the same device have three solutions.

| Solution | When to use | Cost |
| :--- | :--- | :--- |
| Dual-port memory | Two simultaneous accesses in an FPGA memory block | One block with two ports |
| Two single-port copies | Two simultaneous accesses and rewriting by the In-System Memory Content Editor in Quartus Lite | Twice the blocks, with the same content in both copies, rewritten together |
| A single-port device with an arbiter | A chip that has a single interface, such as the SDRAM and the FLASH chip | Accesses are serialized, and one master waits for the other, as in [sdram_arbiter](../ram/sdram_arbiter.md) and [flash_arbiter](../cache/flash_arbiter.md) |

The Quartus Lite of this project does not compile a two-port `altsyncram` together with `ENABLE_RUNTIME_MOD=YES`, which is what gives access through the In-System Memory Content Editor. So the FLASH of the internal memory design uses a single true dual-port copy without that hint, [flash](../rom/flash.md), with port A on instruction fetch and port B on data reads. Rewriting goes through a loader of its own, [flash_loader](../rom/flash_loader.md), which writes port B over JTAG only while the core is halted.

## 6. Stored word width different from the core word

The core speaks in 32-bit words, with a 4-bit mask (one bit per byte) and a byte address. When the device stores words of $W \neq 32$ bits, an adapter between the two reconciles the difference. The adapter only sees the byte mask on a write and a whole 32-bit word on a read. It never receives the width of the instruction, because the selection of a byte or halfword and the sign extension happen in the WB stage of the core. The complete treatment is in [MEMORY_WIDTH.md](https://github.com/insper-riscv/Core/blob/main/docs/en/MEMORY_WIDTH.md), and this section summarizes the rules.

### 6.1. Address

The adapter drops the two low bits of the byte address and works with the word index of the core. Misaligned accesses that cross the word arrive as two independent accesses, each with the address of an aligned word, and the adapter treats each one as an ordinary access.

### 6.2. Narrower memory ($W < 32$)

Let $n = 32 / W$ be the number of slices of a core word.

| Form | How it works | Cycles per access | Where it can sit |
| :--- | :--- | :--- | :--- |
| $n$ devices in parallel | Each one receives its slice of the data and of the mask, with the same address | Those of a 32-bit device | Internal memory or the external bus |
| One device, in series | The $n$ slices go out in sequence | $n$ or more | Only the external bus, with `o_ready` |

On a write, slice $k$ (with $k = 0$ the least significant) receives the pieces below.

$$
\text{data}_k = \text{data}[W(k+1)-1 : Wk] \qquad \text{mask}_k = \text{mask}\left[\tfrac{W}{8}(k+1)-1 : \tfrac{W}{8}k\right]
$$

A slice whose mask is all zero does not need to be written. On a read, the slices are read in sequence and concatenated, with slice 0 in the low bits, and the word is only valid when the last one arrives.

$$
\text{word} = \text{slice}_{n-1} \mathbin{\|} \dots \mathbin{\|} \text{slice}_1 \mathbin{\|} \text{slice}_0
$$

The SDRAM chip of the board is the example of the serial case. It has 16 bits, so $n = 2$. A 32-bit word is a burst of two 16-bit beats, the first with the low half and the second with the high half, and a line of four words is a burst of eight beats. The mask of each beat is the complement of the two bits of the core mask for that half, because the `dqm` pins of the chip mask at `'1'`. The read uses no mask.

### 6.3. Wider memory ($W > 32$)

Let $m = W / 32$ be the number of core words in each word of the device. The address bits just above the two low ones choose the 32-bit lane.

$$
\text{lane} = \text{address}\left[\log_2 m + 1 : 2\right]
$$

On a read, the adapter returns only the chosen lane, without shifting it. On a write, it places the 32-bit data in the chosen lane and builds a $W/8$-bit mask in which only the 4 bits of that lane come from the core mask, and the other bytes stay disabled.

| Device | Core mask | Lane | Mask at the device |
| :--- | :--- | :--- | :--- |
| 64 bits ($m = 2$) | `0011` | 0 | `0000 0011` |
| 64 bits ($m = 2$) | `0011` | 1 | `0011 0000` |
| 128 bits ($m = 4$) | `1111` | 2 | `0000 1111 0000 0000` |

A wide word allows moving several core words at once. The data cache uses this in its 16-byte lines, moved by a single request to the SDRAM controller.

### 6.4. Summary of the decisions

| Situation | Solution |
| :--- | :--- |
| $W < 32$ and a single device | Serialize in $n$ slices, on the external bus, with `o_ready` |
| $W < 32$ and $n$ devices | Put them in parallel, at no cycle cost, with the slice of the mask in each one |
| $W > 32$ | Choose the lane by the address and replicate the data on a write |
| No byte mask on the device | Read, merge and write, only on the external bus |
| The device needs more than one cycle | External bus with `o_ready`, never the internal memory |
