# boot_memory

Single-port internal ROM IP that holds the SoC boot program (the BOOT_MEMORY).

## 1. Role of the component in the SoC

The BOOT_MEMORY occupies the start of the address space (`0x00000000` to `0x00000FFF` in the default map, see [02-barramento-e-memoria.md](https://github.com/insper-riscv/Core/blob/main/docs/pt-br/contracts/02-barramento-e-memoria.md)) and gives the fetch stage the instruction of the PC when it points into that range. The content comes from the initialization file written by the full Quartus compilation; according to the VHDL header, no test rewrites it over JTAG, unlike the FLASH ([flash](flash.md)). The BOOT_MEMORY does not go through the instruction cache.

## 2. Interface

### 2.1. Generic

| Generic | Type | Default | Meaning |
| :--- | :--- | :--- | :--- |
| `size_bytes` | `positive` | 4096 | Size in bytes, a power of two; sets the width of `i_address` and the word count |

### 2.2. Ports

| Port | Direction | Width | Default | Meaning |
| :--- | :--- | ---: | :--- | :--- |
| `i_address` | input | $\log_2(\text{size\_bytes}) - 2$ | | Word index (byte address without the two low bits) |
| `i_clk` | input | 1 | `'1'` | Memory clock |
| `i_rden` | input | 1 | `'1'` | Read enable |
| `i_wren` | input | 1 | `'0'` | Write enable |
| `i_data` | input | 32 | zeros | Write data |
| `o_q` | output | 32 | | Word read |

## 3. Behavior

### 3.1. Block memory instance

The read is done by an instance of [block_ram](../block_ram/block_ram.md), which wraps the `altsyncram` of Quartus' `altera_mf` library, and the other megafunction parameters are fixed there. The generics passed to the instance are:

| Generic | Value |
| :--- | :--- |
| `operation_mode` | `SINGLE_PORT` |
| `word_count` | $\text{size\_bytes} / 4$ (1024 by default) |
| `address_width` | $\log_2(\text{size\_bytes}) - 2$ (10 by default) |
| `init_file` | `./boot_memory_init.mif` |

### 3.2. Read latency

The address is captured on the edge of `i_clk` and the output has no extra register, so the word of the address applied on an edge appears on `o_q` after it, with one cycle of synchronous latency. The instance gets no `instance_name`, so the memory has no `ENABLE_RUNTIME_MOD` hint and the Quartus In-System Memory Content Editor does not see it.

### 3.3. Initialization file

The `.mif` is generated by the board build flow from the platform boot code. The IP size must agree with the BOOT_MEMORY limit configured in the core and in the platform configuration file.

## 4. Integration

The `.qip` file (`src/ROM/Cyclone-V/boot_memory.qip`) lists `block_ram.vhd` and the IP's VHDL, with no family tag.

| Top | Instance | Wiring |
| :--- | :--- | :--- |
| DE0-CV board top (Insper-RISC-V) | `BOOT_MEMORY` | `i_address` on bits 11 to 2 of the fetch address, `i_clk` on the IF stage clock, `i_rden` on the fetch enable, `i_wren` at `'0'`, `o_q` on the core Boot memory data |

In GHDL simulation the equivalent simulation model is [rom_simulation](rom_simulation.md).

## 5. Verification

No `tests/python/tests.json` entry covers this IP, because it needs Intel's `altera_mf` library, absent from the continuous integration image (see the [README](../../../README.en.md)). What exercises it is the hardware top simulation in the Tests repository. `make paths` checks that the `.qip` exists.
